# The Standard — El Estatuto 1.0.0

This is the normative text of El Estatuto: what every framework of the house — the governor and
each employee — looks like, names, documents, verifies and speaks. Clauses carry identifiers of
the form `E-n.m`. A clause marked **[gate]** is enforced by the control of the same identifier in
`estatuto gate`; the others bind by review and by the agent directive. The owner's edition,
`ESTATUTO.md`, carries the same identifiers; the two are kept in parity by the gate itself.

Words: *must* is a requirement; *should* is a recommendation whose omission needs a recorded
reason; *may* is a permission.

## E-0 Purpose, scope and authority

- **E-0.1 Scope.** The standard governs *form*: repository shape, documentation, naming, tooling,
  verification, the protocol and the discipline of change. It never governs *substance*: what a
  framework is, promises and refuses belongs to that framework's charter.
- **E-0.2 Roles.** A repository declares one role: `governor` (La Generala: owns missions, grants,
  budgets, acceptance), `employee` (a framework with a craft that proposes and never accepts), or
  `standard` (this repository alone). Every role is a framework: self-contained, provider-neutral,
  installable and testable without any other framework's code.
- **E-0.3 Authority.** Within a framework, its charter governs substance and the standard governs
  form. When the two collide, a decision is opened in the standard; a local exception is never the
  first answer.
- **E-0.4 Conformance.** Conformance is declared (`estatuto.toml`), measured (`estatuto gate`) and
  continuous (the gate runs in CI on every push). A repository that cannot be measured is not
  conforming.
- **E-0.5 Exceptions.** A deviation from one control is recorded as a dated exception backed by a
  decision record and a sunset (E-8.1). Silent drift is a defect.

## E-1 Identity

- **E-1.1 Declaration [gate].** `estatuto.toml` at the root declares `name` (the persona, `El` or
  `La` followed by a capitalised name), `slug` (lowercase identifier), `role`, `package` (Python
  package) and `standard` (the standard version followed). Optional tables: `[language]` with
  `archive` globs and `proper_nouns`; `[changelog]` with `normative_prefixes` and
  `normative_files`; `[[exception]]` entries. Only El Estatuto declares `role = "standard"`.
- **E-1.2 Names and layout [gate].** The distribution is `<slug>-framework` (the standard itself
  is `estatuto`); the package lives at `src/<package>/` and is imported by that name. The persona
  appears in prose; the slug appears in identifiers, namespaces and file names.
- **E-1.3 One version [gate].** `src/<package>/version.py` is the single source of the version, a
  semantic version. `pyproject.toml`, `CHANGELOG.md` (a `## <version>` section) and, for an
  employee, `manifest.json` agree with it; conformance fails when they drift.
- **E-1.4 Repository identity.** A framework is identified by its persona, its slug and its git
  remote. Local paths are descriptive and never appear in the live surface. The standard's
  `registry/frameworks.json` records the frameworks of the house.

## E-2 Repository root

- **E-2.1 Mandatory files [gate].** `README.md`, `AGENTS.md`, `CONTRIBUTING.md`, `CHANGELOG.md`,
  `PROJECT_MAP.md`, `pyproject.toml`, `uv.lock`, `mkdocs.yml`, `.gitignore`, `.python-version`,
  `estatuto.toml`; for an employee, `manifest.json`; for a governor or an employee,
  `conformance.py` or a documented `<cli> conformance` command.
- **E-2.2 Mandatory directories [gate].** `src/`, `tests/`, `docs/`, `.github/workflows/` with at
  least one workflow, `gates/` with at least one corpus `<name>-gate-v<semver>.json`; for a
  governor or an employee, `contracts/`.
- **E-2.3 Disposable trees ignored [gate].** `.gitignore` ignores at least `.venv/`, `work/`,
  `dist/` and `site/`. Nothing under a disposable tree is a source of truth.
- **E-2.4 Generated files.** `manifest.json`, `contracts/*.json`, `docs/governance/program-status.md`,
  history indexes and recorded evidence are generated by a command named in `CONTRIBUTING.md` and
  never edited by hand. A hand edit of a generated file is a defect even when its content is right.

## E-3 Documentation

- **E-3.1 Diátaxis [gate].** `docs/index.md` and the four quadrants — `tutorials/` (learning),
  `howto/` (tasks), `topics/` (understanding), `reference/` (facts) — each with at least one page.
  A page belongs to exactly one quadrant.
- **E-3.2 Decision records [gate].** `docs/decisions/` holds records named `NNNN-slug.md` (a
  legacy series such as `DK0-NNN-slug.md` may continue for a framework that already has one) and an
  `index.md` that lists every record. A record has a status, a context, a decision and its
  consequences; it is superseded by a new record, never edited to say something else.
- **E-3.3 Governance [gate].** `docs/governance/CHARTER.md` states what the framework is and is not
  (its Núcleo Rector, in the house's word). `docs/governance/baseline/` holds the frozen design
  description(s); `BASELINE.sha256` records `<sha256>  <file>` for each and the gate verifies the
  hashes. `docs/governance/program-status.md` is derived, never edited by hand. A requirement
  ledger (`docs/governance/requirement-ledger.json`) should exist for a framework with a
  requirement-bearing baseline.
- **E-3.4 Project map [gate].** `PROJECT_MAP.md` lets another agent continue without conversation
  history. It has sections on identity and current state, the authority hierarchy, the layout, how
  to change the framework, and verification.
- **E-3.5 Agent rules [gate].** `AGENTS.md` points at `docs/governance/CHARTER.md`, lists the
  verification chain to run before declaring work done, and that chain includes `estatuto gate`.
  It states what is generated, what is frozen, and what is never done.
- **E-3.6 README [gate].** `README.md` has sections that say what the framework does (and refuses
  to do), a quickstart, the documentation map, how to verify a change, and the current status with
  its honest limits.
- **E-3.7 Site [gate].** `mkdocs.yml` builds strictly (`strict: true`) from an explicit `nav`.
  The Material theme is the house theme; archival material is excluded from the site and indexed
  instead.
- **E-3.8 Changelog [gate].** `CHANGELOG.md` follows Keep a Changelog and always has a
  `## Unreleased` section; every released version has a `## <version> — <date>` section.
- **E-3.9 Authority hierarchy.** `PROJECT_MAP.md` states the hierarchy in this order: the standard
  (form) · the charter · the frozen baseline · decisions · the declared public surface (contracts,
  capabilities) · tests, conformance and gates · derived status · README. A lower document that
  contradicts a higher one is corrected, never obeyed.
- **E-3.10 History.** Plans, evidence and reports of past increments stay where gates hashed them,
  are indexed by a derived `docs/history/INDEX.md` when they exist, and are never rewritten. A plan
  declares scope and gate; it creates no normative obligation by itself.

## E-4 Language

- **E-4.1 English live surface [gate].** Every root Markdown file and every page under `docs/`
  not covered by an archive glob is English prose. Identifiers, docstrings, comments, messages,
  data descriptions and commit messages are English.
- **E-4.2 No machine-specific paths [gate].** The live surface contains no absolute path of any
  machine.
- **E-4.3 The archive keeps its language.** Frozen baselines, historical plans, evidence,
  history indexes and decision records accepted before the standard was adopted keep the language
  they were written in and are listed under `[language].archive`. A frozen document is never
  translated: its hash is its identity; a decision record is never edited, so it is never
  translated either.
- **E-4.4 Fixtures.** Test fixture payloads may use any language when language neutrality is under
  test; new fixtures prefer English otherwise.
- **E-4.5 The owner's edition.** The standard's Spanish edition is the only Spanish live document
  of the house. It carries the same clause identifiers as this text and the gate verifies the parity
  (E-9.1).

## E-5 Naming

- **E-5.1 Contract files [gate].** Every file under `contracts/` is a JSON Schema named
  `<name>-v<semver>.json` whose `$id` is `<owner>.<name>/<semver>`; the owner is `peg` under
  `contracts/peg/` and the framework's slug elsewhere. Files are rendered from models (E-2.4).
- **E-5.2 Tests [gate].** Test files are `tests/**/test_<subject>.py`, named after the subject
  they protect, never after the process that produced them (`phase`, `sprint`, `session`, …).
- **E-5.3 Protocol identifiers [gate].** `emp_<slug>01` is the employee id; capability ids match
  `cap_[a-z0-9][a-z0-9_-]{7,63}`; pack ids `pack_…`; tenant ids `ten_…`; mission ids `mis_…`.
  The `01` suffix is the instance of the persona; a second deployment of the same persona is `02`.
- **E-5.4 Plans [gate].** Increment plans, when kept, are `docs/plans/<FAMILY>-<NN>-slug.md`,
  the family in capitals and the slug lowercase.
- **E-5.5 Schema identifiers.** A published document is identified by `<owner>.<kebab-name>/<semver>`.
  Protocol documents use snake_case fields. A domain contract keeps its owner's casing but publishes
  an identifier and a JSON Schema under `contracts/`.
- **E-5.6 Error codes.** Error codes are `UPPER_SNAKE_CASE`, published in the manifest, each with
  its own wording for limitation and next step. The protocol reserves the meaning of
  `CONTRACT_INVALID`, `PROTOCOL_UNSUPPORTED`, `CAPABILITY_UNSUPPORTED`, `AUTHORITY_REQUIRED`,
  `POLICY_BLOCKED`, `BUDGET_EXCEEDED`, `PROVIDER_UNAVAILABLE`, `DEPENDENCY_UNAVAILABLE`,
  `EVIDENCE_INSUFFICIENT`, `HUMAN_INTERVENTION_REQUIRED`, `TERMINAL_CONDITION_UNMET`,
  `IDEMPOTENCY_CONFLICT`, `CANCELLED`. A policy refusal is `POLICY_BLOCKED`, never
  `CONTRACT_INVALID`; a provider payload the contract cannot accept is `PROVIDER_UNAVAILABLE`.
- **E-5.7 Cases and gates.** Conformance cases are `<FAMILY>-NNN`; gate identifiers are
  `<Letter><n>-slug`; a gate corpus is `gates/<name>-gate-v<semver>.json` with a `schema`, a
  `purpose`, `cases` binding requirements to test node ids, and `required_score` equal to the
  number of cases. There is no averaging.
- **E-5.8 Commits.** Commit messages are `type: summary` in English, with type in
  `feat · fix · docs · refactor · test · evidence · release · chore · style`, and a body that says
  why when the summary cannot.

## E-6 Tooling and verification

- **E-6.1 Build [gate].** uv resolves and locks; hatchling builds; `requires-python` declares a
  floor of at least 3.12 and `.python-version` pins 3.12 or newer. A framework may require a newer
  interpreter and records why in a decision.
- **E-6.2 Tools [gate].** `ruff`, `mypy`, `pytest`, `pytest-cov`, `mkdocs` and `pip-audit` are
  declared development dependencies.
- **E-6.3 Floors [gate].** `[tool.ruff]` is configured; `[tool.mypy] strict = true`; branch
  coverage has a floor of at least 80 that is never lowered. Per-module floors should exist and rise
  with coverage.
- **E-6.4 CI [gate].** The workflow runs, on push and pull request: the changelog gate, `ruff check`,
  `ruff format --check`, `mypy`, `pytest` with coverage, the repository's own conformance and gates,
  `estatuto gate`, `pip-audit`, `uv build` and `mkdocs build --strict`.
- **E-6.5 Definition of done.** A task is finished when its behaviour is a general abstraction, not
  a special case; any change across the public boundary is versioned; failure states are honest;
  costs and evidence are traceable through receipts; deterministic tests exist in proportion to
  risk; the whole verification chain passes; and the documentation describes exactly what exists,
  again.
- **E-6.6 Gates.** Every promise a framework makes has an executable gate: `<cli> gate <name>
  --output work/<name>.json` produces a result document with a schema identifier. A green test
  means the declared corpus ran; it never by itself means a horizon is approved.
- **E-6.7 Evidence.** Evidence is recorded by scripts, hash-linked to the sources it observed, and
  never edited by hand. When a source legitimately changes, the evidence is re-recorded in a dated
  increment with the same script; a recorded hash that matches nothing is a defect.

## E-7 The protocol: PEG/1

- **E-7.1 Ownership and vendoring [gate].** The Governed Employee Protocol belongs to the standard.
  Its documents are published under the `peg.` namespace, rendered from `estatuto.peg.contracts` to
  `schemas/peg/`, and vendored verbatim by every governor and employee under `contracts/peg/`; the
  gate compares bytes. No framework defines a protocol shape of its own.
- **E-7.2 Manifest [gate].** An employee publishes `manifest.json`, a `peg.manifest/1.0.0`
  document rendered from its declarations, whose `integrity_digest` is the SHA-256 of the canonical
  JSON of the manifest without the digest field (E-7.14). Any consumer can recompute it.
- **E-7.3 Referenced contracts [gate].** Every contract identifier the manifest names — input,
  output, evidence, deprecated inputs — that is not a `peg.` document has a JSON Schema at
  `contracts/<name>-v<semver>.json`.
- **E-7.4 Surface documented [gate].** `docs/reference/` documents the three routes —
  `POST /peg/v1/assignments`, `GET /peg/v1/manifest`, `GET /peg/v1/health` — and the manifest
  identifier.
- **E-7.5 Reserved codes [gate].** An employee publishes at least `CONTRACT_INVALID` and never
  publishes a reserved code under another spelling or with another meaning.
- **E-7.6 Profiles.** Every employee implements `CORE` (identity and versions, capabilities,
  negotiation, states, evidence, errors, cost, idempotency, cancellation, proposed result).
  `FRAMEWORK` adds a persistent service with its own administration and health; `CONTEXT_PROVIDER`
  adds context requested and delivered with provenance, sufficiency, partiality, receipt and
  validity, without becoming an authority over the mission.
- **E-7.7 Negotiation.** A governor sends a `peg.compatibility-demand/1.0.0`; compatibility requires
  every material field to match a declared capability exactly — protocol version, profiles, mode,
  capability id and version, input, output and evidence contracts, checkpoint. The decision is
  `accept` or `reject` with stable reasons, before an assignment exists. There is no `latest` and no
  silent downgrade. A shared capability id never implies substitutability.
- **E-7.8 Transports.** An employee offers the protocol through an in-process port and, when it runs
  as a service, through HTTP on the three routes. A JSON round trip changes nothing; a test proves
  the equivalence. Request bodies are bounded; nobody obtains authority by reaching an open port.
- **E-7.9 Assignment, result, refusal.** A `peg.assignment/1.0.0` carries the exact context
  capsule and its digest and conveys no authority. A `peg.result/1.0.0` attests the same tenant,
  mission, obligation, assignment, generation and context digest, carries evidence references,
  provenance, observed and unsettled cost, and the domain payload under the capability's output
  contract; it is always a proposal. A `peg.refusal/1.0.0` is returned when nothing can be
  executed, with the HTTP status of its error code: `CONTRACT_INVALID` 400, `BUDGET_EXCEEDED` 402,
  `AUTHORITY_REQUIRED` and `POLICY_BLOCKED` 403, `IDEMPOTENCY_CONFLICT` 409, `PROTOCOL_UNSUPPORTED`
  and `CAPABILITY_UNSUPPORTED` 422, `PROVIDER_UNAVAILABLE` and `DEPENDENCY_UNAVAILABLE` 503, any
  other code 422.
- **E-7.10 Governor obligations.** The governor negotiates before delivering; admits each employee
  version per tenant through an event-sourced administration plane (publish, validate, test,
  certify, admit, observe, canary, rollback, suspend, quarantine, retire); rejects a result that
  conveys authority or whose identity fields differ from the assignment; keeps the cost ledger; and
  alone accepts or rejects work.
- **E-7.11 Employee obligations.** The employee has no runtime dependency on the governor;
  proposes and never accepts; makes cost equal the sum of its receipts; keeps states honest; treats
  `assignment_id` with `generation` as the idempotency key; and scopes cancellation to the
  assignment without revoking any grant.
- **E-7.12 Bindings and grants.** Tenant identity and workload identity are never inferred from each
  other or from text. A `peg.tenant-binding/1.0.0` declares the correspondence between the
  governor's tenant and a provider's tenant; a `peg.workload-binding/1.0.0` authenticates a workload
  and conveys no tenant. A `CONTEXT_PROVIDER` is consumed under two grants — the governor's
  assignment grant and the provider's own context grant — and a context package is evidence, never
  authority.
- **E-7.13 Protocol versioning.** Versions are exact. An additive change to a document is a new
  minor version negotiated explicitly with a coexistence window; a breaking change is a new major.
  Every active mission pins its versions. Additive capabilities such as composed-context transport
  are published as separate documents (`peg.context-transport-support/1.0.0`), never inferred from
  a profile or a name.
- **E-7.14 Canonical JSON.** Where the protocol digests a document, the digest is SHA-256 over the
  UTF-8 bytes of the JSON serialization with keys sorted, separators `,` and `:` without spaces,
  and non-ASCII characters unescaped.

## E-8 Change discipline

- **E-8.1 Exceptions [gate].** Every `[[exception]]` names an existing control, cites an existing
  decision record, states a reason and a sunset date in the future. An expired exception waives
  nothing and is itself a finding.
- **E-8.2 Changelog gate [gate].** CI runs `estatuto changelog-gate --base <ref>`: a change under a
  normative prefix or to a normative file records itself under `## Unreleased` or the build fails.
  Workflow files and the lock file are tooling and may change alone.
- **E-8.3 Deprecation [gate].** `CONTRIBUTING.md` states the policy: a deprecated element keeps
  working for at least one minor release after the release that deprecates it, is listed with its
  replacement and its removal version, and changes nothing silently in the meantime.
- **E-8.4 Decisions.** A decision the code depends on is a record (E-3.2) before the code lands. A
  change that removes an option, a dependency or a guarantee needs an alternative, a compatibility
  analysis, a deprecation window and a migration path.
- **E-8.5 Public contracts.** A published contract's validation rules never change in place. A
  payload that was valid must stay valid under the same identifier; otherwise a new version is
  published, the old one frozen and declared deprecated.
- **E-8.6 Changing the standard.** A clause that becomes stricter, or a protocol document whose
  shape changes, is a major version of the standard: every framework re-measures and the changelog
  names the migration. An additive clause or document is a minor. Wording and tooling are patches.
  Every change is a decision record here first.

## E-9 The standard itself

- **E-9.1 Parity [gate].** `ESTATUTO.md` and `docs/standard/STANDARD.md` carry the same set of
  clause identifiers.
- **E-9.2 Self-measure.** The standard declares `role = "standard"` and passes its own gate.
- **E-9.3 The template is the executable standard.** `estatuto new-employee` produces a repository
  that passes the gate and its own tests at birth; a clause that the template cannot satisfy is a
  defect in one of the two.
- **E-9.4 Registry.** `registry/frameworks.json` lists the frameworks of the house with persona,
  slug, role, package, remote and charter summary. It describes; the gate measures.
